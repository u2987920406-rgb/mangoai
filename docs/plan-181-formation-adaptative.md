# Plan #181 — Générateur de formation adaptative à la demande
*Conçu par Fable 5, 2026-07-03 · corpus d'étude : `docs/corpus-fable/` · exécutable sans moi (fenêtre → 2026-07-07)*

> Donne un sujet (« le TOEIC », « la photographie argentique », « TypeScript avancé ») → Mango fabrique une **formation complète et adaptative** : une APP web (Vite), pas un PDF — structure pédagogique réelle, leçons, exercices, quiz, **ET** un moteur adaptatif : modèle de l'apprenant persistant, répétition espacée, adaptation du niveau en temps réel, génération d'exercices ciblés sur les erreurs.

---

## 1. Contexte & contraintes

### 1.1 Ce que Raf demande (roadmap-game-changer.md, #181, P0, XL)
- **Ergonomie & logique d'apprentissage** : progression pédagogique réelle (prérequis → notions → pratique → évaluation), pas un dump de texte.
- **Sources VÉRIFIÉES** : chaque affirmation traçable, contrôle anti-hallucination.
- **Composants vérifiés** : textes lisibles, schémas quand ils clarifient — décidé par le sujet, pas systématique.
- **Adaptatif au contexte** : un cours de code ≠ un cours d'histoire ≠ un cours de cuisine.
- **Version ambitieuse retenue** : moteur adaptatif complet (modèle apprenant persistant, répétition espacée, adaptation temps réel, exercices ciblés sur les erreurs).

### 1.2 Le précédent réel : TOEIC Quest (2026-06-30, `workspace/toeic-quest/`)
La leçon la plus importante de ce chantier est DÉJÀ payée. TOEIC Quest a prouvé :
- **Le découpage moteur/contenu fonctionne** : moteur bâti à la main (curriculum 52 modules, scoring pondéré, moteur de voix H/F, carte de parcours), **contenu rédigé par GLM** (~290 questions, `run-toeic-content.ts`) validé par schéma strict, images Pexels réelles, cohérence image↔texte jugée par le VL local (`run-toeic-coherence.ts`).
- **Le point faible** : tout était **spécifique au TOEIC** (specs en dur, runner externe, moteur non réutilisable) et **rien n'est adaptatif** — pas de modèle de l'apprenant, pas de répétition espacée, déverrouillage par bilans seulement. `eleve-content.ts`/`eleve-content-tools.ts` ont depuis **généralisé** la génération (`genere_contenu`) et la vérification d'images (`verifie_coherence_images`) — nés exactement de ce manque.
- **Choix produit validé par Raf** : mono-utilisateur d'excellence, **pas de backend par formation**, voix navigateur ($0), persistance localStorage.

### 1.4 Contraintes non négociables
- **Qualité en situation réelle au-dessus de tout** (règle ⭐⭐⭐ de Raf) : build-vert ≠ réussi ; Gardien jamais désactivé ; vraies images ; parcours joué.
- **Gates opt-in, off = byte-identique** (discipline prouvée par la revue Fable) : tout comportement nouveau est gaté ; défaut OFF sauf décision explicite de Raf.
- **Standards à la périphérie, custom au cœur** ; **ne jamais présenter une cible comme un acquis**.
- **Transmission** : Mango produit la formation (GLM $0), Claude/Opus outille — on ne code pas le contenu à la place de l'Élève.
- Cerveau local impossible (mur L51) : la fabrication passe par GLM cloud + escalade Maître plafonnée.

## 2. Décisions d'architecture

### D1 — Le moteur est un TEMPLATE (starter), le sujet est de la DONNÉE
**Décision.** Créer un **starter technique** `server/templates/formation/` (comme `vitrine/`, `phaser/`) : le moteur pédagogique complet, écrit une fois, testé une fois — écrans (placement, carte de parcours, leçon, exercice, session de révision, bilan), moteur de répétition espacée, modèle de l'apprenant, client de sync, machine d'états de quiz. Ce qui **varie avec le sujet** est de la donnée et de l'habillage générés par Mango : le **curriculum** (JSON), les **banques de contenu** (JSON par module), l'**identité visuelle** (palette ancrée au sujet, typo par registre — axiomes design), et d'éventuels **composants spécifiques au domaine** (moteur de voix pour une langue, runner de code pour TypeScript) ajoutés par le run agentique. Ratio visé : ~70 % template / ~30 % généré.

**Alternatives rejetées.**
- *Tout générer par sujet (zéro template)* — c'est ce qu'a coûté TOEIC Quest : le moteur (scoring, voix, déverrouillage) a demandé l'essentiel de l'effort et n'est PAS réutilisable. Regénérer un moteur adaptatif (FSRS, modèle apprenant, sync) à chaque formation, par GLM, c'est garantir des bugs subtils dans la partie la plus critique — exactement ce que la règle « qualité situation réelle » interdit. Le contenu EST le produit (manifest `education.md` : « le contenu bâclé trahit tout ») ; le moteur, lui, doit être du code de confiance.
- *Tout en template (formation = remplir des trous)* — viole « adaptatif au contexte » : un cours de TypeScript a besoin d'exercices de code exécutables, un cours de photo a besoin d'images comparées, une langue a besoin d'audio. Le starter fournit les types d'items UNIVERSELS (qcm, flashcard, texte-à-trous, appariement, leçon) ; le run agentique AJOUTE les types spécifiques en respectant l'interface `ItemRenderer` du moteur.
- *Étendre le manifest `education.md`* — piège repéré : `education.md` décrit une app de QUIZ mono-session (10 questions, 3 minutes, confetti). Une formation est un produit multi-semaines avec curriculum, mémoire et reprise — un autre genre. On crée un manifest dédié `formation-complete.md` SANS toucher `education.md` (les quiz simples continuent d'exister).

### D2 — Le modèle de l'apprenant vit en DOUBLE RÉSIDENCE : app (vérité) + collection partagée (miroir pour Mango)
**Décision.** Le modèle de l'apprenant (maîtrise par compétence, journal de révisions FSRS, historique d'erreurs, position dans le curriculum) est :
1. **Vérité locale dans l'app** : `localStorage`/IndexedDB via un store du template (`lib/learner-store.ts`). L'app marche 100 % hors-ligne — précédent TOEIC, et exigence de robustesse (le backend :3000 n'est pas toujours lancé).
2. **Miroir dans une collection partagée** `/api/shared/formation-<slug>` (= scope Blackboard `shared:formation-<slug>`, SQLite persistant) : le client du template pousse chaque événement d'apprentissage (best-effort, file d'attente rejouée quand le backend revient), et lit les extensions de contenu poussées par le Tuteur (D4) via SSE avec repli polling — pattern EXACT de `MANGO_DATA_RULES` (scenario.ts), déjà spécifié et éprouvé pour les apps générées.

Clés du scope : `learner` (modèle courant, un doc), `events:<ts>` (journal append-only borné, prune TTL possible — `SqliteStore.prune` existe), `bank-ext:<module>` (banques d'extension écrites par le Tuteur).

**Alternatives rejetées.**
- *Blackboard en accès direct depuis l'app* — impossible et faux problème : le Blackboard est du SQLite serveur, pas une API navigateur. Le rail REST/SSE `/api/shared` existe précisément pour ça (#138) ; il est CORS-ouvert aux apps générées et cross-framework. Réinventer une sync serait la faute cardinale « réinventer le rail existant ».
- *SQLite dédiée par formation via la brique `db` (backend généré)* — j'ai failli la choisir (c'est « propre » sur le papier). Rejetée pour la V1 : chaque formation traînerait son Express (port, orphelins — plaie documentée du port 3000 —, install, sécurité), alors que le choix produit validé sur TOEIC est « mono-utilisateur d'excellence, pas de backend ». La brique reste la voie du futur multi-apprenants/vente (É7) : l'interface `learner-store` du template est écrite pour permettre ce swap (localStorage → API) sans toucher les écrans.
- *localStorage seul* — Mango serait AVEUGLE : pas de lecture du modèle apprenant → pas d'exercices ciblés → la « version ambitieuse » retenue par Raf tombe. C'est le statu quo TOEIC, explicitement dépassé par #181.
- *Tout dans le Blackboard, rien en local* — l'app meurt quand le backend est éteint ; viole la dégradation gracieuse imposée partout dans le repo (mangoData : « never crash on a failed fetch »).

### D3 — Répétition espacée : FSRS (lib `ts-fsrs`), avec repli Leitner pur
**Décision.** Le moteur de révision du template utilise **FSRS** (Free Spaced Repetition Scheduler — l'algorithme par défaut d'Anki depuis fin 2023, nettement supérieur à SM-2 à charge de révision égale, paramètres par défaut utilisables sans entraînement). Implémentation : la lib **`ts-fsrs`** (MIT, TypeScript, zéro dépendance), **embarquée dans le starter** (dépendance du `package.json` du template, installée au scaffold — pas de réseau au runtime) et ajoutée à la liste blanche d'`add_dependency`. Par-dessus, une fine couche maison `lib/spaced.ts` : mapping item→carte, files de révision du jour, et **repli Leitner** (5 boîtes, intervalles fixes) en pur JS si la lib venait à manquer — le moteur ne casse jamais.

**Alternatives rejetées.**
- *SM-2 maison* — j'ai failli le choisir pour sa simplicité (30 lignes, zéro dépendance). Rejeté par la RÈGLE GRAVÉE de `fondation.md` : « avant toute recommandation technique, vérifier qu'aucun standard mature ne couvre le besoin ; toujours la solution la plus avancée, jamais la plus familière ». SM-2 (1987) est le choix familier ; FSRS est l'état de l'art éprouvé à grande échelle, et `ts-fsrs` le rend aussi simple à intégrer.
- *FSRS réimplémenté maison* — violer « ne jamais réinventer un standard mature » pour économiser une dépendance de 20 Ko serait absurde ; les 21 paramètres et la fonction de puissance de FSRS sont faciles à se tromper, durs à tester.
- *FSRS avec optimisation des poids par apprenant* — l'optimiseur (fsrs-rs / py) demande des milliers de revues et un runtime lourd. Hors V1 ; les poids par défaut sont documentés comme bons. Noté en piste d'évolution.

### D4 — Boucle adaptative à DEUX VITESSES : rapide dans l'app (déterministe), lente côté MangoOS (le Tuteur)
**Décision.** L'adaptation « temps réel » n'a pas besoin d'un LLM ; la génération ciblée, si. On sépare :
- **Boucle RAPIDE (client, dans le template, déterministe, offline)** : estimation de maîtrise par compétence (EWMA sur les réponses, pondérée difficulté — même esprit que le scoring TOEIC existant), sélection du prochain item (files FSRS dues > compétences faibles > progression du curriculum), ajustement de difficulté (monter/descendre d'un cran de `difficulty` selon la maîtrise), déverrouillage de modules par seuils. Réponse en < 1 ms, testable en pur.
- **Boucle LENTE (serveur, le « Tuteur », asynchrone)** : un job `formation-tuteur.ts` (déclenché par le nocturne/cron existant, ou à la demande) lit `shared:formation-<slug>`, diagnostique les faiblesses PERSISTANTES (le spine pur décide : compétence sous seuil malgré N tentatives, patterns d'erreur récurrents), et **génère un lot d'exercices ciblés** via `generateContentItems` (le sujet du lot cite les erreurs réelles de l'apprenant), le valide (schéma + images + échantillon d'exactitude, D5), puis l'écrit en `bank-ext:<module>` dans la collection. L'app l'absorbe par SSE ou au prochain chargement — **sans régénérer l'app**.

**Alternatives rejetées.**
- *L'app appelle un LLM en direct* — latence de 30 s à 4 min par item (mesurée sur l'Esthète), nécessite une clé API dans le frontend (interdit : « NEVER put secrets in frontend .env »), casse l'offline. L'apprentissage tolère très bien l'asynchrone (les exercices ciblés d'aujourd'hui répondent aux erreurs d'hier — c'est même pédagogiquement sain).
- *Adaptation = régénérer l'app (nouveau run agentique par ajustement)* — coût énorme (Gardien complet à chaque passe), risque de régression du moteur à chaque écriture, et confusion code/donnée. Le contenu est de la DONNÉE : il voyage par la collection, jamais par `write_file`.
- *Un vrai modèle IRT (Item Response Theory) côté client* — sur-ingénierie pour un produit mono-apprenant : l'IRT calibre les items sur des POPULATIONS. EWMA par compétence + FSRS couvrent le besoin réel ; honnêteté : c'est une heuristique, pas de la psychométrie (inscrit en §4).

### D5 — Vérification du contenu : validation déterministe systématique + volet PÉDAGO du Gardien (exactitude par échantillonnage sourcé)
**Décision.** Trois étages, du moins cher au plus cher :
1. **Déterministe, systématique, à la génération** (déjà existant, réutilisé) : schéma strict par type d'item (`validateItems` + validations spécifiques calquées sur `run-toeic-content.ts` : nb de choix, réponse dans les bornes, pas de doublons, explication présente), seuil de lot ≥ 60 % + retry, `verifie_coherence_images` (VL local) pour tout item illustré.
2. **Déterministe, à la clôture** — nouveau volet du Gardien, gate `ELEVE_GATE_PEDAGO` (opt-in) branché dans `runClosureGate` comme les volets balance/placeholders : couverture curriculum↔banques (chaque module a ses items, chaque compétence déclarée est exercée), leçon avant exercice, sources présentes (chaque leçon porte `sources:[url…]` non vides), lisibilité mesurable (longueur de phrase/leçon bornée).
3. **Exactitude factuelle par ÉCHANTILLONNAGE, jugée** : le volet tire N affirmations vérifiables (défaut 10) des leçons, relit leurs sources déclarées (`lire_page`), et demande au juge « cette affirmation est-elle supportée par cette source ? » ; sous un seuil de support, raison de correction (le nudge existant du Gardien renvoie l'Élève corriger/re-sourcer). Point de branchement futur : `brain-ensemble.ts` (C3, posé non-câblé) pour un vote à 2-3 cerveaux sur les affirmations douteuses — le rôle « juge » est exactement celui que le plan Pilier C déclare éligible.

Cas particulier des domaines à **vérité formelle** (code, maths) : la vérification n'est PAS un juge mais une exécution — les exercices de code du curriculum portent des tests, et le volet les LANCE (le mécanisme `ELEVE_GATE_TESTS`/`runProjectTests` existe déjà dans le Gardien). Toujours préférer le déterminisme au jugement quand il existe.

**Alternatives rejetées.**
- *Vérification exhaustive de chaque affirmation* — une formation de 40 modules × 10 leçons × 5 affirmations = 2000 vérifications web+juge par formation : des heures et un coût prohibitif, pour un juge lui-même faillible. L'échantillonnage + les sources obligatoires + la traçabilité (l'apprenant VOIT les sources dans l'app) donnent l'essentiel de la valeur ; l'exhaustif n'est même pas atteignable honnêtement (juge bruité). Limite inscrite au registre (§4).
- *Confier la vérification à MangoQA* — contresens architectural : MangoQA « ne reçoit d'ordres de personne, n'écrit jamais dans le système » (fondation.md §V). La vérification de contenu est un GATE de production → c'est le territoire du Gardien de clôture (#161). MangoQA observera les patterns d'échec du volet PÉDAGO dans la durée (Visage 2), comme pour tout le reste.
- *Aucune vérification d'exactitude (schéma seul)* — c'est le statu quo TOEIC (personne n'a vérifié que les 290 explications de grammaire sont justes). Acceptable pour un quiz jetable, pas pour « des formations que Raf veut utiliser pour de vrai et vendre ». La règle « qualité en situation réelle » tranche.
- *Génération « sourced-first » stricte (n'écrire que des paraphrases de pages lues)* — séduisant contre l'hallucination, mais il ferait exploser le nombre d'appels web par leçon et produirait un contenu patchwork. Compromis retenu : leçons rédigées par le modèle AVEC sources déclarées obligatoires + contrôle par échantillon.

### D6 — Fabrication multi-sessions : le MANIFEST de formation est l'état durable ; un module = un run borné
**Décision.** Fabriquer une formation complète est un travail de plusieurs heures/sessions. L'état inter-runs vit dans un fichier **`formation.json` à la racine du projet généré** (le manifest) : sujet, curriculum complet, et **état par module** (`a_faire | genere | verifie | integre`), plus les décisions figées (palette, types d'items retenus, sources maîtresses). Le pipeline (É3) est une boucle *par module* : chaque module = **un run agentique borné** (génération de contenu + intégration) qui se clôt par le Gardien, coche le manifest, et rend la main. Relancer la fabrique = relire le manifest et reprendre au premier module non-`verifie` — le pattern EXACT du `state.json` resumable de `run-toeic-content.ts`, promu en objet de première classe. À l'intérieur d'un run, `ELEVE_RESUME` (snapshot v2, réparé par la revue pré-#181 précisément pour ce chantier) couvre le crash ; `ELEVE_ETAT` + budget B0.1 couvrent la dérive.

**Alternatives rejetées.**
- *Un seul run agentique géant (« fabrique-moi la formation », 36 itérations)* — mathématiquement impossible : 40 modules ne tiennent ni dans `ELEVE_AGENTIC_MAX_ITER=36` ni dans le budget contexte ; et un échec au module 30 perdrait tout. La revue Fable a durci la reprise, pas aboli les bornes.
- *L'état dans le plan #160* — piège vu : `eleve-plan.ts` est explicitement « éphémère, in-process » (Map), il meurt au redémarrage. Le plan reste le fil d'UN run ; le manifest est le fil de LA formation.
- *L'état dans le Blackboard* — le manifest décrit un ARTEFACT du projet (il doit voyager avec le dossier de l'app, être lisible par l'apprenant-développeur, versionnable) ; le Blackboard est pour le savoir cross-projet. La progression de l'APPRENANT, elle, va bien dans la collection partagée (D2) — deux états, deux résidences, ne pas confondre.
- *Pattern « Gros Projet » #139 (mode `projet` + Kanban) tel quel* — proche mais pensé pour un humain dans la boucle (incréments validés au chat). La fabrique est un RUNNER (comme `run-toeic-content.ts`) pilotable aussi sans humain (nocturne). On réutilise son ESPRIT (socle puis incréments bornés), pas son UI.

### D7 — L'app est générée UNE fois, elle ÉVOLUE par la donnée
**Décision** (synthèse de D1+D4) : le cycle de vie d'une formation est : *scaffold du starter → spécialisation par le run agentique (habillage + composants domaine + intégration des banques) → clôture Gardien → l'app vit seule* ; ensuite **tout ce qui change transite par la collection partagée** (modèle apprenant qui monte, banques d'extension du Tuteur qui descendent). On ne rouvre un run agentique sur l'app que pour une évolution du MOTEUR (bug, nouveau type d'item) — jamais pour du contenu.

## 4. Risques & limites honnêtes

1. **L'exactitude factuelle est ÉCHANTILLONNÉE, jamais garantie** (D5). Un volet PÉDAGO vert signifie « N affirmations tirées au sort sont supportées par leurs sources », pas « la formation est vraie ». Pour vendre une formation, une relecture humaine experte reste nécessaire. → `limites.md` : *opération bloquée = certification d'exactitude exhaustive ; piste = vote multi-cerveaux (C3) + relecture humaine ; Codable en interne 🟡 ; ⚖️ Sonnet ; M*.
2. **La qualité rédactionnelle de GLM est variable.** TOEIC a montré des lots à 60-100 % de validité avec retry ; sur des sujets pointus (TypeScript avancé), le taux de rejet montera et l'escalade Maître coûtera. Le seuil de 60 % + retry est un filet, pas une garantie de style. Mitigation : le manifest `formation-complete.md` impose des exemples de « bonne leçon » ; mesurer le taux de rejet par domaine (métrique à logger dès É3).
3. **Le mur des médias** : pas de génération vidéo (voir_video LIT, ne produit pas) ni de schémas complexes fiables (SVG génératif = qualité aléatoire). V1 : texte + vraies photos Pexels + schémas SVG simples seulement quand le run les réussit ; les « vidéos quand elles apportent » de la roadmap restent une CIBLE. Audio : voix navigateur, qualité dépendante de l'OS (L62 déjà inscrite).
4. **La boucle adaptative lente dépend d'un backend vivant.** Backend éteint = app pleinement fonctionnelle mais Tuteur muet et modèle apprenant non miroité (file de sync locale rejouée au retour — perte possible si le localStorage saute avant). Assumé pour un produit local mono-utilisateur.
5. **La maîtrise estimée est une heuristique** (EWMA), pas de la psychométrie : elle peut sur/sous-estimer sur peu de données (démarrage à froid → le placement initial du template compense en partie). Ne jamais la présenter comme un « niveau certifié ».
6. **Coût et durée de fabrication** : une formation 40 modules ≈ plusieurs heures de GLM cloud + quelques escalades. Le mur L51 interdit le $0-local ; le garde-fou coût de MangoQA (Visage 1) et le budget B0.1 bornent, mais Raf doit savoir qu'une formation complète n'est pas « 5 minutes ».
7. **Risque de collision de scope `shared:`** : les collections partagées n'ont qu'un contrôle d'accès déclaratif (`X-MangoApp-Id`). Deux formations au même slug se marcheraient dessus — le slug inclut donc un suffixe unique posé par la Fabrique dans `.mangoapp.json`.
8. **Interaction des gates sur run long** : la config nominale (`ELEVE_ETAT`+`ELEVE_RESUME`+`CLOSURE_GATE`+`PEDAGO`) n'a jamais tourné ENSEMBLE — la revue pré-#181 a prouvé que c'est exactement là que les défauts se cachent. É4 doit ajouter ses scénarios à `test-fondations-gates-combines.ts` (le volet PÉDAGO sous reprise, notamment).
9. **Dérive « quiz déguisé »** : le risque produit n°1 est de livrer un gros quiz au lieu d'une formation (leçons squelettiques, tout dans les QCM). Garde : le volet PÉDAGO impose leçon-avant-exercice et un ratio minimal leçon/exercices par module ; le manifest de domaine martèle « la leçon est le produit, l'exercice est la preuve ».

### 5.3 Heuristiques employées (réutilisables)
- **« Chercher le rail avant de poser des rails »** : avant chaque décision, grep du besoin dans le repo (sync app↔OS → `/api/shared` existait ; génération validée → `eleve-content.ts` existait ; runner resumable → `run-toeic-content.ts` existait). Sur 7 décisions, 5 sont des assemblages, 2 seulement des créations (starter, volet PÉDAGO). C'est la même trouvaille que le Pilier C (« dispatch propage déjà → boucher 4 trous ») : dans un repo mûr, la bonne architecture est surtout de la CARTOGRAPHIE.
- **Boucle rapide / boucle lente** : quand « temps réel » et « LLM » apparaissent dans la même phrase, les séparer d'office — le déterminisme au plus près de l'utilisateur, l'intelligence en asynchrone. Vaut pour l'adaptativité ici, valait pour le Gardien (critique async) et MangoQA (verdict async surfacé après coup).
- **Un état = une résidence = une question de survie** (« survit-il au crash ? au redémarrage ? à l'extinction du backend ? »). Poser la question pour CHAQUE donnée avant de choisir où elle vit.
- **Le précédent réel bat le design de principe** : TOEIC Quest a arbitré moteur/contenu, backend/pas-backend, et révélé les manques exacts (`eleve-content-tools.ts` : « comble la lacune repérée en construisant TOEIC Quest »). Toujours chercher « la dernière fois qu'on a essayé ».
- **Dimensionner la vérification au coût du faux positif** (cf. 5.1.5).
- **Nommer les limites au moment de la décision, pas après** : chaque « rejeté » de §2 qui laissait un résidu de valeur (exhaustivité, IRT, optimisation FSRS, multi-utilisateur) est devenu soit un point d'extension déclaré, soit une entrée de §4. Rien ne se perd — c'est la règle du registre des limites, appliquée à la conception elle-même.
