# Revue globale MangoOS — moteur de génération + MangoQA + boucle nocturne (2026-07-03)

Revue d'architecture **en lecture seule**, menée **avec un regard neuf** (aucune connaissance préalable supposée), sur le SYSTÈME ENTIER — pas un delta : le moteur de génération (`server/src/eleve*.ts`, `agent.ts`, `scenario.ts`, kernel + routage cerveau), MangoQA (dépôt séparé `D:\IA\MangoQA`, 3 visages + Flux/Suite), et la boucle nocturne autonome (`nocturnal.ts`, `train-loop.ts`, `run-*.ts`). Méthode : lecture directe du code (jamais les seuls commentaires), 3 sous-revues parallèles sur clusters, recoupées par une lecture personnelle du cœur transverse (kernel, ponts Bus/MangoQA, brain-dispatch, nocturnal). **Aucun fichier applicatif modifié, aucune commande git.** Reprise du chantier laissé ouvert par Fable 5.

## Verdict d'ensemble

**Un moteur mûr, discipliné et honnête — avec un angle mort structurant : la partie qui tourne sans humain est aussi la moins gardée.** Le cœur est d'une qualité rare pour un projet perso : séparation pur/impur exemplaire (boucles testables sans réseau), kill-switch réel non décoratif, timeouts durs + killTree, sécurité shell (allowlist, secrets rédigés, anti-SSRF), résumabilité universelle après crash, et une `fondation.md` v2 qui distingue explicitement RÉEL/PARTIEL/ASPIRATIONNEL (le rêve n'est plus déguisé en acquis). 

Mais trois vérités d'architecture ressortent, convergentes entre les trois clusters :
1. **La boucle nocturne contourne toute la fabrique QA** — elle génère hors du Bus, ne demande aucun audit MangoQA, et n'a pour seul garde-fou que ses propres deadlines de temps. Le « circuit breaker nocturne » du Disjoncteur est structurellement aveugle à la boucle qu'il est censé garder.
2. **MangoQA peut SIGNALER, pas ARRÊTER.** La `fondation.md` §V affirme « il peut ARRÊTER, jamais créer ». Dans le code, MangoQA n'a aucun canal de retour : il écrit des verdicts JSON que personne ne consomme pour bloquer quoi que ce soit ; côté MangoOS le verdict est injecté comme **message de chat consultatif, en asynchrone fire-and-forget**. L'« arrêt » est un rêve d'architecture.
3. **La « liquidité de cerveau » (Pilier C, donnée « largement acquise » §VIII.c) ne couvre PAS la génération principale.** Le fallback inter-providers protège les appels one-shot (`getBrain().complete`, dispatch) — mais le moteur de génération réel passe par `query()` du SDK, cerveau **claude-only sans repli**. Claude tombe la nuit → la nuit est perdue, sans bascule.

Aucun de ces trois points n'est un bug de code : ce sont des **écarts entre ce que le système prétend garantir et ce que le code garantit réellement**. C'est exactement la matière qui doit éclairer #180 (interface de bureau autonome) et #176 (Stratège global proactif) : on ne peut pas construire un pilotage autonome sûr sur une autorité d'arrêt qui n'existe pas et une boucle nocturne hors observabilité.

## Ce qui est sain (confirmé, à préserver)

- **Séparation pur/impur exemplaire, partout.** La boucle Élève (`eleve-runtime.ts`), le Gardien (`eleve-gate.ts`), le Disjoncteur (`disjoncteur.ts`) et les visages MangoQA sont des fonctions **pures sur des deps injectées** — testables sans réseau, cloud ni navigateur, horloge injectée pour le déterminisme. C'est une discipline rare et la vraie valeur défensive du projet.
- **Kill-switch réel, pas décoratif.** `shouldAbort` est lu en frontière d'itération, sortie `aborted:true` **avant** tout appel/écriture → aucun état corrompu. Le snapshot compresse `tool_calls` + trace pour éviter l'I/O O(n²) (déjà durci par la revue Fable).
- **Sécurité d'exécution solide.** Timeout dur 120 s/commande + `killTree`, fetch Élève borné + backoff sur 429/503, `FORBIDDEN_RUN` blacklist, `buildRestrictedEnv()` qui n'expose jamais les clés API aux commandes du modèle, vault de secrets rédigé, anti-SSRF sur les outils web. Périmètre d'action cohérent.
- **`jsonl.ts` (MangoQA) — vrai bon travail.** Lecteur borné anti-OOM + incrémental à curseur, gestion des lignes tronquées, rotation (fichier rétréci → reset), cap octets. Mutualisé et raisonné (#L70/#Q5).
- **Honnêteté d'ingénierie institutionnalisée.** `fondation.md` v2 marque RÉEL/PARTIEL/ASPIRATIONNEL ; `limites.md` registre les murs (L51) ; `FAILLES.md` documente et traite les failles connues (dans le typecheck) ; fail-open ≠ fail-silent est une discipline (`console.warn` partout, seul ENOENT reste muet). Le système ne se ment pas à lui-même — c'est ce qui rend cette revue possible.
- **Résumabilité universelle.** Chaque runner a son fichier d'état + `atomicWriteFileSync` → reprise propre après crash/coupure SSE.

## Annexe — trace de raisonnement

*Partie demandée pour distillation méthodologique (aborder un système inconnu de grande taille).*

**Démarche adoptée.** J'ai refusé de faire confiance à la documentation comme source de vérité (elle décrit la CIBLE) et je l'ai lue comme une **carte des prétentions à vérifier** : `fondation.md` §V « MangoQA peut ARRÊTER », §VIII.c « liquidité cerveau acquise », MEMORY « Gardien TOUJOURS actif ». Chaque prétention forte est devenue une question de vérification dans le code. Puis : cartographie quantitative d'abord (449 fichiers `.ts`, mais tri par taille/date révèle que le cœur tient en ~10 fichiers, le reste = `test-*`/`run-*`), fan-out de 3 sous-revues parallèles sur clusters (moteur / MangoQA / nocturne) pendant que je lisais moi-même la **couture transverse** que nul cluster ne voit seul (kernel ↔ ponts Bus/MangoQA ↔ nocturnal). C'est cette couture qui a produit les 3 constats majeurs — ils vivent tous *entre* les modules, pas dedans.

**Alternatives d'approche rejetées.** (1) *Lire linéairement les gros fichiers d'abord* (`eleve.ts` 117 Ko) — rejeté : on se noie dans le détail avant d'avoir la carte des flux ; j'ai délégué la lecture profonde et gardé la vue système. (2) *Faire confiance aux tests verts comme preuve de correction* — rejeté frontalement : la propre MEMORY du projet dit « build-vert ≠ réussi », et la revue Fable précédente a trouvé un 🔴 précisément invisible des ~800 tests unitaires (chaque gate testé isolément). Les défauts d'un système gardé vivent dans les **interactions**, pas dans les unités. (3) *Forker mon contexte dans les sous-agents* — rejeté au profit d'agents frais (`general-purpose`) : je voulais des regards **indépendants** qui ne partagent pas mes hypothèses, pour que la convergence soit un signal (et de fait, mes 3 constats transverses ont été confirmés séparément par 2 clusters chacun).

**Heuristiques de priorisation (où regarder).** *« Le danger est là où personne ne regarde la nuit »* → priorité absolue à la boucle autonome. *« Suivre la donnée, pas le code »* → tracer qui ÉCRIT et qui LIT `bus-events.jsonl`, `breaker-verdict.json`, `.axioms.md` a révélé les canaux morts (personne ne consomme le verdict) et les non-canaux (la nuit n'écrit pas sur le Bus). *« Chercher l'écart claim↔code »* : la plus haute densité de bugs d'architecture est là où le système se décrit plus capable qu'il n'est. *« Un fail-open muet est un bug qui se cache »* → grep systématique des `catch {}` vides sur les chemins de qualité.

**Points de bascule (où j'ai changé d'avis).** (1) J'ai d'abord noté « pas de fallback génération » comme 🔴 isolé — puis, en relisant `fondation.md` §IX (cloud assumé, mur L51 nommé), j'ai **rétrogradé en 🟠 + écart de communication** : ce n'est pas un défaut caché, c'est une honnêteté incomplète (le §VIII.c sur-vend). (2) J'ai cru le cost-guard du Disjoncteur totalement décoratif (thèse de l'agent MangoQA, qui ne voyait pas le pont) — puis la lecture de `kernel-chat-bridge.ts` a montré que cost/turns/duration SONT émis **pour les tours de chat** : le réflexe est alimenté pour le chat, aveugle seulement pour la nuit. La nuance a transformé un « décoratif » en un « asymétrique » — plus juste et plus actionnable.

**Ce qui a failli me tromper.** `ripgrep` a signalé `axioms.ts` comme *binaire* (octet NUL à l'offset 5489). Un NUL dans un `.ts` = drapeau rouge classique de corruption/encodage. J'ai failli l'inscrire en 🟠 « fichier source corrompu ». En lisant le contexte réel (`axiomsFingerprint(...).join("\x00")`), c'est un **choix délibéré et correct** : le NUL est un séparateur d'empreinte garanti sans collision (il n'apparaît jamais dans du texte normal), utilisé UNIQUEMENT pour la détection de changement (diff), **jamais injecté dans un prompt**. La leçon rejouée : un signe alarmant hors contexte doit être vérifié dans son usage réel avant d'être un constat — sinon on transforme une bonne idée en fausse faille. C'est le pendant exact du principe qui a rendu cette revue utile ailleurs : ne jamais conclure sur la surface (nom, commentaire, warning d'outil), toujours sur le flux réel.
